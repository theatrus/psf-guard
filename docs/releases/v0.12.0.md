# v0.12.0

PSF Guard 0.12 keeps its own catalogs in sync with Target Scheduler, matches
flats by what they measure, adds stack stretches and Gaia colour calibration,
and backs up on a schedule. Direct Target Scheduler access still works in 0.12
but is deprecated.

## Deprecations

**PSF Guard is moving to its own catalogs.**

For new Target Scheduler databases, choose **Settings → Databases → Import
from Target Scheduler** to import the database and set up sync.

Your current Target Scheduler setup will keep working in 0.12. A later update
will create a PSF Guard catalog for you and keep captures, plans and grades in
sync with Target Scheduler.

Separate catalogs let us add features to PSF Guard and support new Target
Scheduler versions. We plan to remove direct database access in 0.13 or
later. Direct CLI/API access also keeps working in 0.12. See
[Importing](https://github.com/theatrus/psf-guard/blob/v0.12.0/docs/IMPORTING.md).

## Upgrading from 0.11

- **Choose how Target Scheduler syncs.** New Target Scheduler connections
  create a PSF Guard-owned catalog. Sync on startup, when new images or grades
  arrive, or on a schedule. Automatic grade writeback has its own switch.
  New local-file imports enable automatic sync and grade writeback; review
  those settings after importing. Manual planning and grade transfers still
  use Preview and Apply. Director activation sends approved planning through
  the saved TS connection and retries failed deliveries.
- **Allow time for calibration checks and rebuilds.** The first start reads
  frame sites, grades calibration frames and measures flat groups in the
  background. Stacks and masters rebuild once when you next use them. PSF
  Guard does not reuse plate solves or satellite predictions made by 0.11, so
  it solves frames again. Work you start takes priority over these checks.
- **Review new targets and planning changes.** Automatic image-folder import
  now holds frames for unknown targets for Review. Change New targets in the
  database settings to create projects automatically. Before activating a
  plan, check its preview: activation turns off exposure plans the plan does
  not include. Take Target Scheduler’s values keeps plans made in N.I.N.A.
- **Calibration session links change once.** A link saved by 0.11 may open
  the first session instead. Open the session again and save its new link.
- **Keep a copy of settings before a downgrade.** PSF Guard 0.11 can open
  catalogs graded by 0.12, but it ignores the new calibration grades and
  choices apart from darks graded for stray light. Saving settings in an
  older version drops the new calibration settings and rig overrides.

## Highlights

- **Keep your catalog separate from Target Scheduler.** Import a Target
  Scheduler database into a PSF Guard catalog, or pair the PSF Guard Sync
  plugin. Keep captures, plans and grades in sync, with grade conflicts
  reported for review.

- **Inspect calibration frames and masters.** Review calibration grades,
  compare frames with their sessions, trace master inputs and repair duplicate
  records. Keep a frame out or use it anyway without deleting its file.

- **Match flats by their measured pattern.** Group flats across nights by
  measured light patterns and dust changes. Inspect dust and vignetting, split
  or join groups, and choose which side of a change supplies a light’s flats.

- **Stretch stacks and combine color.** Use Median anchor or Layered alongside
  the default Auto MTF stretch. Install Gaia colors to calibrate RGB, LRGB and
  one-shot-color stacks. Combine WBPP masters in their own color card. Rebuilt
  stacks keep your processing choices.

- **Plan mosaics across rigs.** Place and rotate panels separately, preserve
  panels already captured and preview what each rig will shoot. Resend an
  activation to a site that missed it. In the Starfront collaboration beta,
  deliver accepted lights with calibration frames or completed stacks.

- **Back up now or on a schedule.** Save settings, accounts, plans and
  catalogs in one archive. Download it, save it to a folder, or schedule daily
  or weekly backups with retention limits.

- **Review images on any screen.** Browse by each rig’s observing night,
  select Sequence frames by score, stars or HFR, and keep charts in view.
  Compact phone layouts leave more room for images. Desktop Zoom in and Zoom
  out resize the whole UI.

- **Control background work.** Follow progress and reorder queued builds in
  the header’s jobs list. Pause automatic quality analysis, preview pre-generation, flat measuring or frame-site reading until Resume or a server
  restart. Builds and color requests survive restarts, and work you start
  takes priority.

### Catalogs, imports and sync

- **Import from Target Scheduler** creates a PSF Guard-owned catalog and keeps
  the source for automatic capture imports and grade writeback. Configure sync
  on startup, when images or grades change, or on a schedule. The same flow
  also offers a catalog and pairing setup for the PSF Guard Sync plugin. Image-folder
  import stays available alongside both TS choices. Conflicting TS
  grades are reported without overwriting them.

- Database-file imports can create a standalone catalog copy, preserving
  existing PSF Guard data without connecting the source. **Catalog storage**
  offers **Use a custom database path (advanced)** for database-file imports,
  image folders and Sync plugin catalogs. Existing catalogs are not replaced.

- Automatic import no longer creates projects on its own. Frames for targets
  the catalog does not have wait, and the database's status line offers
  **Review** to preview and import them; **New targets** in its settings
  can leave them out or create projects as before. Scan rules leave
  autofocus frames, tests and other folders out of every import, with exclude
  and include patterns and filters for frames with no image type, no target
  name or a short exposure. A `.psfguardignore` file skips its folder.

- Automatic import no longer changes what Target Scheduler will shoot in
  projects it did not create. There it only adds image rows to exposure
  plans that already exist, and leaves their counts alone. Frames that would
  need a new plan wait for **Review** with the rest. The import preview now
  says which plans an import adds or raises.

- Import matches lights to exposure plans with the same exposure length,
  filter and binning. Gain, offset and readout mode must match or use the
  camera default (-1). This avoids false missing-plan warnings and duplicate
  templates. When a new plan is needed, import reuses a template with matching
  filter, binning and default exposure length, allowing -1 for the other
  settings. Otherwise, it creates a template with the lights’ gain, offset and
  exposure length. Different exposure lengths use separate templates; groups
  assigned to one template share a plan.

- Scan rules also apply when an import starts inside an excluded or ignored
  folder, including imports started from **Review**. If you enter a full path
  as a pattern, the error shows the pattern to use instead. Automatic import
  does not reread unchanged lights excluded by its filters.

- Sync, import and export previews start immediately; a newer preview replaces
  one still running. In **Data Transfer** and **Remote PSF Guard**, changing
  options stops the current preview so you can preview the new choices.
  Starting an import also replaces its running import preview.

- The transfer preview counts the **Keep out** and **Use anyway** choices a
  pull brings, since they change the destination's masters, and a choice
  made on the destination stays with a file the source cataloged under
  another ID.

- The reload button left the header. **Rescan image folders**, under ⋯ in
  Images and Sequence, looks for image files added since the last scan
  (folder tree and files together; no Shift-click). PSF Guard still rescans
  a database's folders on its own every five minutes and after sync and
  automatic import.

- Saving a project or adding an exposure plan no longer fails with "database
  is locked" when a background pass or N.I.N.A. is writing to the catalog at
  the same moment. The save now waits for that write to finish. Imports,
  syncs, forgetting calibration frames, and moving or restoring rejects wait
  the same way.

### Calibration frames and masters

- A **Calibration** page shows a database's calibration library: its sessions
  by night, kind and settings, each frame as a picture drawn for its kind,
  and a flat divided by the rest of its session so that drying dew stands
  out from dust. Beside each frame are its grade and its numbers next to its
  session's, with **Keep out**, **Use anyway**, validity marks and
  **Forget**. ← → flip through a session. A **Masters** tab lists every
  master with its sources and the projects using it, and opens any of them
  without a stack. Open it from Settings › Databases or a project's
  Calibration report. It replaces the calibration library dialog; the URL
  preserves its filters and choices.

- **Calibration** opened from a project shows the calibration that project
  uses: the sessions its lights' masters are built from, flat grouping's
  choices included, the masters they calibrate with, and only the flat
  groups they touch, across every rig the project was shot with. An
  **M 44 on Askar 120 ✕** chip heads the filter bar; ✕ or **Show all of
  Askar 120's calibration** widens to the rig's whole library. Opened from
  the Library, it shows the whole library as before. On Calibration the
  header's Rig · target control shows only the rig.

- Calibration › Frames keeps its sidebar in view: the session or group
  list stays beside the frame as the page scrolls, fits the window, and
  scrolls on its own, so its last groups and its pager stay in reach.

- The Calibration page has a tab in the header, between Sequence and
  Stacks. It follows the database in the header's scope rather than keeping
  its own, and with a project in scope it opens on that project's rig. A
  stack's master inspector opens a master on the page with **Open in
  Calibration**.

- PSF Guard grades every bias, dark, dark-flat and flat in the calibration
  library as OK, suspect or poor. Flats are judged against the rest of their
  session for clipping, exposure, the light pattern and spots that come and
  go, such as drying dew; bias and darks against the frames that could stand
  in for them for level, noise, banding and hot pixels. Poor frames stay out
  of masters and WBPP exports, and stacks that used them are built again. A
  dark that caught stray light is one kind of poor frame.

- The calibration library shows each frame's grade and its main reason, and
  each night counts the frames kept out. **Keep out** leaves a frame out of
  masters and exports without forgetting it, so a rescan does not bring it
  back; **Use anyway** puts a poor frame back; **Clear** lets the grade
  decide again. Choices travel with the frames when catalogs sync.

- A suspect calibration frame can be overruled. **Use anyway** in
  Calibration › Frames now appears on a suspect frame as well as a kept-out
  one. The frame then counts as OK: it shows **Used anyway**, its session
  counts it as OK, and the lights its masters serve lose the suspect
  frames Check. Its masters stay as they were. **Clear** brings the grade
  back, and a regrade keeps the choice.

- On the Calibration page, **Keep out** is offered for every frame, even one
  its grade already keeps out, so you can keep a frame out by hand the way
  you reject a light, and a later grade cannot bring it back. Such a frame
  shows **Kept out by hand**.

- **Use anyway** now puts a dark graded for stray light back into its
  master. Master building screens darks for stray light itself only while
  some dark in the set has no grade yet, and a master's record lists only
  the frames it combined. After the upgrade, each dark and dark-flat master
  whose frames are all graded builds once more, and so do the flats and
  stacks built on it. A newly imported dark set builds twice: screened
  before grading reaches it, then without the screen once it is graded.

- Grading runs in the background when the server starts, after each import,
  and two minutes after remote uploads of any calibration frame stop, and
  gives way to work you are waiting for.

- PSF Guard checks darks and dark-flats sent by remote upload for stray light
  once uploads pause for two minutes, as it does after an import; before,
  they waited for the next server start. The calibration library shows each
  measured dark's level and spread, in ADU.

- A calibration frame that is on disk twice, such as a copy a filer has not
  yet cleaned out of the drop folder, is catalogued once. When the original
  goes, its row moves to the copy and keeps its grade and marks, instead of
  staying behind as a missing file. The Calibration page's **Duplicates**
  filter lists exposures an older import recorded twice, and **Repair
  duplicates…** previews and then merges them into one row each and rebuilds
  the masters built from them. A later pull from a catalog that still has
  the duplicates does not bring them back. No file is moved or deleted.
  `psf-guard calibration repair-duplicates <db> --dry-run` does the same from
  the command line.

- **Repair duplicates** on the Calibration page works on large libraries
  behind a reverse proxy. Before, Apply waited for any stack build in
  progress and could end in a gateway timeout with nothing repaired. The
  check and the repair now run as jobs, on the page and in the header's job
  line: "Checking files 812 of 2,140", then "Merging 37 of 203", with
  Stop. A stopped repair writes nothing. Apply no longer fails because a
  stack recorded a master or grading ran since the preview. When the
  duplicates themselves changed, it shows what changed and the new plan.
  The list shows when the check ran. It checks again in the background
  when the calibration rows have changed since. Read-only accounts see it
  too. The CLI and server cannot repair the same catalog at the same time.

- The Library flags projects whose lights the calibration library serves
  poorly with a **Poor** or **Check** pill, worked out in the background:
  lights it cannot calibrate (now also lights from a camera with no
  calibration frames at all), thin dark masters, flats that carry changing
  spots, old or mixed flats, suspect frames in use. The pill opens the
  Calibration report, whose new **Quality** section counts the lights by
  night and filter, and **Show › Calibration issues** lists just those
  projects.

- A project's calibration coverage report leaves rejected lights out, so a
  night you rejected no longer shows up as lacking flats or darks.
  **Include N rejected lights** adds them back.

- An image's detail view has a **Calibration** panel: the light's
  calibration findings in words, and for each kind the frames its master
  would take, by night and sensor temperature, with suspect, kept-out,
  unused and refused frames and why. Choosing a finding picks out the frames
  behind it, such as the two nights a flat master mixes, and the choice
  stays as you move between images. The 🧪 chip in Images and Sequence now
  opens the light on that panel.

- Calibration health catches up on its own. A light whose file was missing
  is judged again once a directory refresh finds it or the image folders
  change. New lights from N.I.N.A. or a CLI regrade are judged once the
  Library or an image view looks, within a couple of minutes and after any
  grading pass. Judging a project again reads only the lights whose file
  changed, and a server that stops ends the work between lights. The first
  pass after the upgrade judges every project and reads every light's
  header once.

- A night's "can't be calibrated" link in the coverage report opens only
  that night's lights, and Images keeps that night when you change another
  filter.

- On the Calibration page, stepping through flats in compare mode stays in
  the comparison instead of flashing back to the plain frame and losing the
  zoom. Changing database clears the last database's rig and filters, and
  each project opens on its own rig unless you chose one by hand.

- A calibration session's address no longer changes when a colder or
  warmer frame joins the session. Every dark and flat session gets a new
  address once with this version, so a link saved before it opens the first
  session instead.

- Calibration checks can be tuned in **Settings › Calibration**: the
  matching tolerances, the dark-master choices, every light check and every
  frame-grade limit. A light check can flag, be advisory (shown as Check,
  never "can't calibrate", so stacks keep the light) or be off. Under
  **Rigs**, any of them can be set for one rig, such as a rig that shoots
  sky flats or can't cap for darks, while everything else inherits; presets
  for sky flats, a dark library and no darks fill the form to review. A
  light's Calibration panel lists the limits it was checked by, who set
  them, and what a setting kept from being flagged, and opens its rig's
  settings. The defaults are the limits used before. WBPP exports and runs,
  and `psf-guard export`, match by the same settings. With **Leave out
  lights that can't be calibrated** on, every export leaves out the lights a
  stack would, in either layout, from the CLI and in the AstroBin export,
  and says how many and why. The WBPP runner scripts list the settings in
  force and warn about frames an earlier export left in the folder. An
  older PSF Guard that saves its settings drops the rigs' values and the new
  settings, so set them again after a downgrade.

- Forgetting a calibration frame now always shows the next one, not
  sometimes the first.

### Flat matching and observing nights

- Flats are matched by what they measure, not only by the rotator angle
  they record. Angles whose flats measure alike are one **response
  family**, named in Calibration › Frames by its measured angle range
  (`72.6° & 82.2°`). A light takes its family's flats at its own angle
  first, and another angle's only where they measured alike with its own
  angle's, the family's flats at the two angles measure alike on several
  sessions and nights (from the light's side of every change), or its own
  pixels chose the family; a stack then reads it at its flats' angle instead of
  refusing them, and the panel says which span and how many pairs. Where two families lie within
  10° of a light's angle, as after a rotator re-homed, the light's own
  pixels choose between them. They move a light off its recorded angle
  only when its rotator's epochs or another filter's lights agree;
  otherwise it keeps its recorded angle's flats and gets a Check. The
  Calibration panel shows the **Flat family** and how it was chosen.
  Nights of only two flats are measured and grouped too.

- PSF Guard measures how alike each night's flats are and keeps nights
  that differ, such as before and after new dust, out of one master. A
  light takes flats from its own side of each measured change: its own
  angle's when there are some, else the nearest other angle when the rig's
  flats barely depend on the angle, else its own flats corrected across
  the change. The light's Calibration panel says how its flats were
  chosen, and **Flats from across a change** flags a light that had to
  take flats from the other side, or was shot during the change. Nights
  measured alike now mix without the **mixed flats** Check. The
  Calibration page's **Frames** view marks each flat session with its
  group, draws each split and each camera-side change between the
  sessions with why it happened, and compares the two nights' flats. Its
  **Edit limits** opens the three settings under **Settings ›
  Calibration › Flat groups**, which set the limits or turn it off. A new
  **Angle** filter narrows Frames to one rotator angle. `psf-guard flat-groups` measures a copy of a catalog
  from the command line. Exports and WBPP runs place the same flats, give
  lights of one night that need different flats a session each, and list
  the lights WBPP cannot calibrate, as a stack would.

- Flat groups can be split and joined by hand in Calibration › Frames ›
  Groups (**Split here**, **Join**), and a light can be put before or
  after a change, or given one group's flats, from its Calibration panel
  or, for a selection, with **Flat side…** in Images. Your choice wins
  over the measurements and is drawn as yours (*Split by you · Reset*),
  with the measured numbers beside it; a join that crosses a camera-side
  change says so. Choices whose flats or change are gone are kept and
  shown as no longer applied. They travel with Merge catalogs and
  `sync pull`, and need database management to change.

- **Calibration › Frames** can list flat groups instead of sessions:
  **Sessions | Groups** at the top of the sidebar. Groups run newest first
  by filter and angle, with the split between neighbours and its reason
  in between, and mark the current group, one partly measured and one a
  change follows; ↑ and ↓ move between them. A group shows its flats in
  the same image browser as a session, night by night with each night
  marked, then its nights, how alike they measured against the rig's
  limits, the change on each side with Compare, and what it feeds: its
  flat masters and the lights that take it, by project, each linking to
  Images on exactly those lights. The URL stores the selected group. When scoped to a project, the list
  shows that project’s groups with neighbouring groups dimmed.

- Calibration › Frames finds the large, faint dust shadows a filter or
  window casts, such as a RedCat61's 600-pixel disks under half a percent
  deep, and an SCT's donuts, and no longer counts a flat's own noise as
  spots. A flat's spots read as `15 spots · 3 large disks`. **Spots** draws
  each at its shape — a disk's rim, a donut's ring and hole, a spot's box —
  with **Large dust** nested under it for the disks, donuts and vignetting;
  each large mark says its depth and, from the header's focal ratio, how far
  in front of the sensor the dust sits. The session comparison overlays dust found in the stacked flats and
  lists the individual flats that contain it. Dust found in only one flat is
  marked as transient. Flat groups count a disk
  or donut that arrives, leaves or moves; dust that moves only as far as
  focus travel explains, such as an SCT's donuts, is drawn but not counted;
  and a guider's corner shadow that turns with the camera counts as
  vignetting. It splits groups only when the light-pattern difference exceeds
  the limit. After the upgrade every flat is graded once more,
  and nothing else reads them again for their dust.

- Flat groups hold up on rigs whose rotator wanders: flats a degree or two
  apart are one angle and are compared, so a change's window ends at the
  first flats that show it. Flats that record no angle take the angle
  they measure alike with when only one fits, and otherwise serve a light
  only when no flat of its angle does, or when they are the only flats on
  its side of a change; lights on such rigs may take new flats, and their
  masters rebuild. Flats shot through a reducer are never compared with
  flats shot without it. A light's own pixels now place it against a
  change of several shadows spread across the frame, so far fewer lights
  shot during a change are flagged. One filter's split across two changes
  no longer merges them into a window of minutes or makes a change of its
  own, a change narrower than one flat run says so in Frames, and flats
  from across two changes are flagged rather than corrected across one.

- Tracked sky flats with stars no longer read as dew or frost: the flat-set
  check counts only spots that take light away, and **Compare with
  session** draws stars at neutral grey.

- **Measuring flats** shows the rig and session count in the header’s jobs list
  and on **Calibration › Frames**. It measures sessions changed by an import,
  sync, upload, forget or duplicate repair, and resumes unfinished work at
  startup. An up-to-date catalog needs no pixel reads. The rig you are viewing
  takes priority without delaying work you start. Changing dust or light-pattern limits regroups stored measurements immediately; switching from
  time-based to measured groups measures only that rig. Missing or unreadable
  files are retried later. **Pause** keeps completed measurements and prevents
  new passes until **Resume** or a server restart, even if flats change
  meanwhile.

- A flat session some of whose files are gone, as flats catalogued both
  where an upload left them and where they were moved, is measured once
  from the flats that read and then left alone, instead of being read again
  on every measuring pass. It is read again when a missing file comes back,
  a file the share or its permissions refused opens again, or a file that
  would not decode is replaced. A session none of whose flats read is no
  longer tried on every pass either; the catalog's flat measurements
  (`psf_guard_flat_response.unread`) keep which flats failed and why. The
  app does not show these yet.

- Calibration splits frames into nights at local noon where each was shot,
  taken from the site longitude in its header (the N.I.N.A. profile's site),
  else its computer's clock, so a dawn flat run that crosses noon UTC stays
  one session and is graded as one. Before, every rig split where the
  catalog's lights were quiet, and a catalog without lights split at noon
  UTC, cutting dawn runs west of Greenwich in two. A rig taken to a star
  party keeps its home nights; a frame with no site of its own splits where
  its rig usually is. A rig with no site in its frames can take a
  UTC offset under **Rig's time zone** in its calibration settings.
  After the upgrade a **Reading frame sites** row in the job line reads
  each frame's site in the background, with **Pause**, and retries while
  the server runs if the NAS is not mounted; the rigs it places are graded
  again and their flat groups planned again: sessions whose date moved are
  renamed without measuring them again, and only runs that were split are
  measured once more. When a frame was shot, from flat-group change windows
  to the strip, the frame panel and the duplicates list, reads on the rig's
  clock with its offset, such as UTC−7; when a master was built reads on
  your clock with its zone.

### Stacks, color and WBPP

- Stacks offer a **Median anchor** stretch beside Auto MTF: it places the
  background median exactly on a target from a robust black point, with
  optional curves boost, highlight compression and normalization. Auto MTF
  stays the default.

- Stacks also offer a **Layered** stretch, which keeps local contrast on
  bright structure, can compress star cores, and can lift saturation without
  shifting hue.

- RGB and LRGB color previews, and one-shot-color stacks, are color
  calibrated against Gaia star colors, so a Sun-colored star comes out white
  and the sky a neutral gray. The card shows the star count and gains, as
  `Calibrated on 143 stars · R ×1.12, B ×0.87`, or the reason calibration was
  skipped. A switch in the processing stack, or a one-shot-color stack's view
  processing, turns calibration off. Install the optional **Gaia colors** catalog
  in Settings › Catalogs, which shows it as its own item with its size,
  whether it is installed, and an **Install** button.

- Seiza updates reuse completed stacks, checkpoints and calibration masters
  when their output is unchanged. If only the display stretch or an OSC
  stack's color calibration is out of date, **Build current set** refreshes
  the card preview from the saved FITS. Queued previews show **Waiting to
  render preview** on the card and in the job list. The stack, processing and
  downloads stay available while the preview refreshes, and a failed refresh
  keeps the old preview. Changes to stacking output, frames, grades or
  calibration still rebuild affected results.

- After an engine update, a stack card shows its refreshed preview as soon
  as the refresh finishes. The build no longer reports completion before
  the new preview is saved.

- With **Chosen by Seiza**, the stack reference now comes from the largest
  orientation group when plate solves show several rotator angles. This
  avoids choosing a reference that excludes most frames for rotation.
  **Orientation group margin** in **Settings → Stacking** sets a margin
  inside Seiza's 10° rotation limit; the default is 1°. Existing stacks keep
  their reference until their frames change or you click **Rebuild**.

- When grading leaves fewer than two usable frames in a channel, its card
  stops showing the old stack and color compositions stop offering that stack
  as a source. Missing files or missing calibration alone do not remove it.

- **Build stacks**, **Build current set** and **Build** on a channel card
  appear in the jobs list immediately as **Preparing stack build**, with **Preparing…** on
  the button. PSF Guard prepares the frames in the background, then shows
  one build per channel. You can stop preparation before the channel builds
  are queued. A build still being prepared when the server restarts comes
  back in its place in the queue.

- Stack preparation reads each calibration file's header once per request,
  instead of once per light. Large projects queue sooner, and other catalog
  requests can continue during preparation.

- The uncalibrated-lights check, calibration report, AstroBin export and
  **Export** read the calibration library once per request. Large checks and
  exports start sooner. **Export** also skips the full image-folder rescan
  before starting.

- Queued stack builds and color previews read frames, grades and calibration
  again when they start. They use grades changed while they waited, and the
  card follows the new build if its frames changed. Artifact searches also
  join the stack queue, ahead of automatic work.

- With **Re-apply processing when a stack refreshes** on (the default), rebuilt
  stacks keep their stretch, deconvolution and RC-Astro choices. After a build
  you start or take over, each channel’s processing runs ahead of your other
  queued builds. Processing after an automatic refresh waits for the refresh
  delay, then behind your work and builds of the same target. Only the newest
  stack is processed. Until it finishes, the card shows the previous result
  with **From the previous stack · reprocessing** and the job’s progress. If
  processing fails, PSF Guard keeps the previous result, shows the reason and
  does not retry automatically.

- Color compositions you start that reuse prepared channels can run
  alongside stack builds. The same applies when no deconvolution or RC-Astro
  is needed and no other composition is preparing the same inputs. After a build you start, a
  target's color can compose once its own channels finish, without waiting for
  other targets' builds.
  Only one short composition runs at a time; queued rows show **Waiting for
  the composition ahead** without a build-queue position. Automatic compositions
  and work that needs new tool results still use the build queue. A composition
  based on an older channel revision cannot replace the latest color preview.

- A color preview requested while its target's channels are preparing, queued
  or building now waits and uses their new stacks. Its card shows **Waiting
  for the channel builds to finish**. The composition survives a server
  restart, and you can stop it while it waits.

- **Combine channel stacks** builds color from WBPP masters in a card marked
  **WBPP**. Before, a project split by exposure put the masters in an
  **Unknown exposure** card that could not be built. Source labels show each
  master's sub-exposure when known. Unless you choose sources in **Custom
  combination**, a card never mixes PSF Guard stacks and WBPP masters.

- A color composition running RC-Astro tools can be stopped from the
  background jobs list, and its row shows the current channel and tool,
  as `H-alpha: BlurXTerminator (42%)`, with progress updates while the
  tool runs. New frames in one channel now rerun the tools on that channel
  only, unless background extraction is on. The color editor's **Use each
  channel's processing** copies the deconvolution and RC-Astro steps each
  channel card shows into the color inputs.

- **Apply processing** in Stacks shows which job it is waiting for, then the
  current processing step and progress. Stretch, deconvolution and RC-Astro
  runs share the build queue and appear in the header’s jobs list. You can
  reorder or remove queued runs, stop a running RC-Astro job, and open the
  target’s stacks from its row. Processing survives a server restart and
  resumes after the last completed tool step. A page left open reconnects to
  the run.

- Stacks of frames rotated slightly between nights no longer show
  cross-hatched bands across a faint sky. The SNR a stack reports on a
  faint sky is lower than before, often by about a tenth, because it now
  measures the sky's real noise; the old resampling smoothed that noise
  and lost no signal doing so. Stacks made before rebuild once.

- The page checks a running stack's status every second. These replies no
  longer include each frame's background map. For a 122-frame stack that cut each
  reply from 1.1 MB to about 70 KB.

- Queued WBPP runs for other databases can start while one database copies
  masters to its process directory, as soon as PixInsight is free. Runs for
  the copying database still wait and keep their queue order.

- WBPP master copies show the current file and file counts in the dialog
  and background jobs list. Copy controls stay disabled while copying, and
  repeat copy requests cannot start a second copy. A run requested while a
  copy starts now joins the queue instead of being lost. The dialog also explains
  PixInsight’s missing Gaia catalog message.

### Planning and mosaics

- **Planning** opens for a selected project even when its catalog has no plan,
  showing catalog warnings and **Retry planning**. Catalog copies excluded
  because they share an identity no longer leave a disabled button or show
  incorrect missing-GUID guidance. Image-folder imports can open their plans
  from the same button.

- A Director plan's status now reads **Activated** or **Needs activating**
  instead of Synced or Not synced, so it is not mistaken for the catalog
  Sync, and the Library badge says **Activated on N rigs** rather than
  Active, Target Scheduler's own project state. The **Activate on the
  rigs** dialog previews by itself when it opens and again whenever its
  inputs change, so there is no Preview button to press. The preview reads
  a copy of each rig's planning tables, so it never waits for N.I.N.A. or
  holds a rig database's lock; **Activate** checks the databases themselves
  and writes only when they match, and when they do not, it says what
  changed and previews again. A plan that cannot be activated yet says
  what to do first instead of offering **Activate…**. Unsaved plan edits
  are never saved unasked: the dialog offers **Save and activate…**.

- While a plan's framing has a locked shot panel, every rig that is on and
  did not shoot it shows its field as an outline where the panel was shot,
  so turning a rig on or picking it shows what it would take there.
  Unticking **Outline** hides it for the visit.

- A plan's mosaic panels are placed one by one. A framed target that already
  has frames starts locked where they were shot, and **Unlock** frees it;
  **Mosaic panels** adds
  panels beside it or round the whole mosaic to the north, east, south, west
  or a corner, as a ring, or by filling holes. With **Panel** you drag one
  panel on the sky: it settles at the minimum overlap, shows what it shares
  with its neighbours, and a drop that would leave a gap or too thin an
  overlap goes back unless you hold Alt or press **Place anyway**. With
  **Snap** off, a dragged panel stays where you drop it, flagged if it
  breaks the overlap rule. An unlocked panel with frames that is moved far or
  turned gets a new Target Scheduler target; the old one keeps its frames. Arrow
  keys nudge the chosen panel, and panel edits undo. Activation adds a Target Scheduler target per new
  panel in the same project and leaves the shot one alone, and the Library
  shows the panels as one mosaic whatever their shape. Saved grids open
  unchanged, as the panels they made.

- A shot mosaic panel is drawn where its frames were taken, with the field
  and angle they were shot with, read from their plate solves, else their
  headers, else the plan. The sky shows a panel's name, small, only when
  the mosaic has more than one panel. New panels use the rig's
  current field and meet a shot panel at its real edges. Each panel is now
  shot at its own camera angle, the plan's turned by north's lean at its
  center, so wide northern mosaics stay square; targets already shot keep
  their angle. A panel can also be turned on its own with its handle, `[`
  and `]`, or a typed turn. Every rig gets each panel's angle, rotator or
  not. A rig framed on its own gets the same panel tools.

- Selecting another rig for a shared mosaic no longer moves its panels to fit
  that rig’s field. Choose **Frame separately** or **Use its field** on the
  rig’s card. Turning a rig off preserves the mosaic’s size. Gap and overlap
  checks cover all rigs’ panels together, so panels from one rig can fill gaps
  between another rig’s panels. A shared edge must meet the larger of the two
  rigs’ minimum overlaps, measured against the smaller panel.

- Activation no longer takes over an existing Target Scheduler target with
  frames that sits more than a quarter of a panel from the panel it would
  stand for: the panel gets a new target, the frames stay where they were
  shot, and the preview shows the distance to the old target.

- With **Snap** on, dragging a mosaic panel along its row no longer moves it
  into a diagonal neighbour's row.

- Director activation uses the catalog's saved TS connection to deliver the
  reviewed project's planning. The preview includes the TS destination;
  failed deliveries stay pending and retry through the existing sync settings.
  A short pending message keeps detailed errors under **Error details**.
  Independent projects retry separately even when grades conflict. Collaboration
  minimum-altitude limits reach TS, and Sync preview refreshes cannot change an
  activation's approval. Captures, grades, acquisition counts and other TS
  projects stay unchanged.

- Changing a filter's template in a plan before its first activation no longer
  leaves the old exposure plan running in Target Scheduler beside the new one.
  Activation turns off an exposure plan for the same target and filter at
  another exposure length. The preview lists it as replaced, and the plan
  shows **Needs activating** until you apply the change.

- A plan shows **Needs activating** whenever activation would change a rig’s
  Target Scheduler plans, including changes made in N.I.N.A. and replaced
  exposure plans that are still on. The summary shows **Activated**, **Needs
  activating**, or **Couldn't check the rigs** when the databases cannot be
  read. The tooltip and banner explain why activation is needed. After the
  first activation, the banner offers **Activate again…**. The preview lists
  each change, such as `desired 100 → 150`.

- The plan now decides which Target Scheduler exposure plans run in each
  rig's project. Activation switches on every plan the plan has, and
  switches off every other plan in the project, frames and counts kept,
  including filters the plan doesn't shoot at all. Two objectives that come
  to the same target, template and exposure share one Target Scheduler plan
  asking for the sum of their frames; progress shows it under each, marked
  shared, and counts it once.

- The activation preview starts with what Target Scheduler will shoot
  afterwards, then what it turns off and why, then what it turns back on,
  and shows the same after **Activate**. The count of turn-offs is in the rig's
  line and in the bar ("Needs activating: turns off 1 plan in ultracat131").

- To keep a plan made in N.I.N.A., **Take Target Scheduler's values**: it
  now brings each exposure length in as its own objective, so a 30 s L plan
  beside the plan's 300 s one becomes an "Unsaturated stars" objective and
  stays on. Planning never adds objectives on its own: a project imported
  from Target Scheduler keeps one objective per filter.

- A scheduling save that conflicts with another edit blocks another save
  until you reload the limits, including while the latest limits are loading.

- A plan whose remote rig's site missed the last activation now reads
  **Needs activating**: "observatory-pi hasn't received this activation" in the summary
  and the bar, and "not sent to observatory-pi" on the rig's line. The bar
  and the activation dialog offer **Send to observatory-pi again**, with the
  error and when it was tried, and show no button when every site has it.
  Once the site answers a connection test, a sync or another push, the
  server sends the activation there on its own.

- Planning no longer shows **PSF Guard was updated** after every reload. A
  cached survey image could report an older build number and trigger the
  notice by mistake.

### Image review and scoring

- Images, Sequence and the image detail split nights at each rig's local
  noon, as calibration does, instead of one split for the whole catalog: a
  light finds its rig through its Target Scheduler profile, so lights a
  western rig shoots after midnight UTC stay on the night they began. The night and hour marks
  can be set to nights and hours, nights only, or off, from **Marks** in
  the View panel or Settings › Review. **Nights end** in
  Settings › Calibration puts lights back on one split for the whole
  catalog with **Same time for all rigs**, for every rig or one, and
  **Nights end** in the View panel shows
  the other split in one view, through its link.

- Images and Sequence mark where frames cross into another night or hour.
  A line and the night's date sit in the gap before a night's first frame,
  alternate nights have a faint background band, and thinner lines mark the hours
  when frames are dense enough for them to help. Nights split at each
  rig's local noon, not at midnight, and no card moves for a mark.

- Images' **Date** groups are observing nights, split at each rig's local
  noon as calibration does: a night west of
  Greenwich no longer lands on the next day's date or across two dates.
  Where one target and filter hold frames from two or more Target Scheduler
  profiles, sequence scoring and statistical grading compare each profile
  with itself, so two rigs merged into one catalog are no longer scored
  against each other. The profile stands for the rig because catalog rows do
  not record the camera or telescope, and reading every frame's header would
  make scoring slow, so one rig kept under two N.I.N.A. profiles now scores
  as two. A catalog with one profile scores as before, including older rows
  with no profile. Two projects with one name stay in separate Project
  groups. Links to groups from before still open them, and the image
  detail's next and previous walk the same nights as the grid.

- Image cards in Images and Sequence take the shape of the frame, read
  once per camera setup from one frame's header, so a square or 4:3
  sensor fills its card as a 3:2 one does. They no longer leave empty
  bands above and below a landscape frame at the smaller thumbnail
  sizes, so more rows fit on screen, and Sequence lays its cards out with
  the same spacing as Images.

- Sequence's **Cutoff** can measure **Stars** or **HFR** as well as the
  score. The chart, the slider and the cutoff rule follow the measure
  chosen; the Stars and HFR sliders run over the readings in the session on
  screen. The score cutoff now reads 0 to 100, as the chips do.

- **Scoring** has two more penalties, **HFR rise** and **Star loss**, from 0%
  to 200%, saved with your other scoring defaults. They set how hard a
  frame is marked down for an HFR above, or fewer stars than, the night's
  good frames, where Max HFR and Min stars only reject past a fixed line.

- Sequence's **Scoring** penalties and reject limits have defaults of
  their own, in **Settings › Review › Sequence scoring**, with **Reset to
  built-in defaults**. Every view starts from them. A change in the toolbar
  now applies to that view only: the URL stores all five values, the
  control reads **Scoring (changed)**, and its popover offers **Save as
  default** and **Reset to default**. Images, the detail view and Stacks
  in the same project follow the change and say so, Stacks beside
  **Build**; another project starts from your defaults. Signed in, the
  defaults follow you to any browser like your other view choices. The
  values the control remembered before become your defaults. Min stars
  now takes a whole number.

- In **Sequence**, the summary, suspect pills and score chart stay below the
  toolbar as you scroll through frames. On short windows, they scroll with
  the page to leave room for the frames. Click a point in **Solved pointing**,
  or focus it and press Enter, to move to that frame without changing your
  selection. Click the chart heading to collapse or expand it; PSF Guard
  remembers this choice in the current browser. The collapsed heading shows
  the solved-frame count and how many have pointing issues.

- The Sequence score chart puts a dot under each bar for the frame's grade:
  green for accepted, red for rejected, faint grey for pending. The bar's
  tooltip starts with the grade and the reject reason, and the dots change
  as you grade, undo and redo.

- In Sequence, each filter's **All sessions** tab stands out: it starts
  its filter's row, with a bar, tint and bold label in its own colour and a
  date-range icon.

- In Sequence, a **Select** rule stays on after you reject its frames, with

- In Sequence, the suspect pills (cloud events, focus drift, tracking
  issues, off target, unsolved) each open a list of their frames. A click

- In Sequence, the **Select** pill says what each rule selects and how many
  frames, and a chosen rule stays on: moving the score cutoff or rescoring

- Sequence disables **Poor calibration** in **Select**, marked *(updating)*,

- Images, Sequence and a mosaic's sequence mark lights the calibration
  library serves poorly with a 🧪 chip: red for Poor, yellow for Check. The

- Images and Sequence can show the newest frames first: **View › Sort ›

- Signed in to a server with user accounts, your view choices follow you to

- Images and Sequence each keep their own thumbnail size: moving between

### Jobs and server operation

- You can pause **Analyzing database quality**, **Generating previews**,
  **Measuring flats** and **Reading frame sites** for each database from the
  header’s jobs list. **Pause** keeps completed work; the row stays **paused**
  until **Resume** or a server restart. New automatic work waits too. Settings
  offers **Resume** for quality analysis, and Calibration offers it for flat
  measuring and frame sites. Quality scans you start still run, and automatic
  stack refreshes do not wait for paused analysis. MCP clients use `pause_job`
  and `resume_job`, which replace `cancel_flat_measuring`,
  `resume_flat_measuring`, `cancel_frame_sites` and `resume_frame_sites`.

- When preview pre-generation is enabled on the server, **Generating previews**
  shows each database’s progress and image count. You can pause it until you
  choose **Resume** or the server restarts. Previews you open still generate
  as needed. When you start a job, pre-generation finishes the images already
  rendering, waits for your job, then continues.

- Quality scans you start now queue when another scan runs on the same
  database. They run before database-wide quality analysis, which pauses and
  repeats its interrupted target afterwards.

- The header's jobs list now includes calibration grading, calibration health
  checks, light-header reads, flat matching and catalog upkeep. It also shows
  previews, imports, exports to the export folder, artifact searches and
  planning transfers to remote sites. Previews, imports, exports, artifact
  searches and star catalog installations have **Stop**. Stopping an import
  rolls it back. Stopping an export keeps completed files; the next export
  skips those files.

- When you add or change a database, PSF Guard builds its query indexes and
  reads older calibration frames' readout modes immediately. The jobs list
  shows this work and the pairing of calibrated copies with their lights.

- Catalog installations show in the header's job line with their progress.
  Settings and the color cards update when an installation finishes.

- The header counts running, queued, waiting and paused jobs separately, along
  with jobs that need your attention. Its list groups jobs under **Started by
  you** and **Automatic**. Jobs that need you appear first, followed by
  running, queued, waiting and paused work. Queued builds show their position,
  such as `queued · 4 · 3 ahead`. Flat measuring shows the rigs left to check
  and those queued for the next pass. Only jobs that need your attention use
  the warning colour.

- In the header's background jobs list, **Move to top** moves a queued task
  under **Started by you** to the front of its stack/processing or WBPP queue.
  It runs next after the current task finishes.

- New builds you start join ahead of queued automatic builds. Starting a build
  pauses a running automatic build, which returns to the queue and resumes
  from its checkpoint after your work. Automatic reprocessing waits behind
  your work and builds of its own target, rather than all targets' builds.

- The header's background jobs keep automatic work in view while your own
  work runs. A database quality analysis, an automatic stack refresh, or an
  automatic processing run interrupted by a build, scan or solve you start
  appears as **waiting** below your work, with its progress and the reason
  it is waiting. Builds you queued count as queued,
  not waiting. An automatic build your build stopped starts again once
  your work has been quiet for 30 seconds, from where it stopped when no
  frame or grade changed meanwhile, and its row turns into the running
  build without appearing twice. One you stopped yourself stays stopped.

- **Purge Rejects** runs **Preview**, **Remove**, **Restore** and **Empty
  trash** as jobs. The dialog and jobs list show progress, such as `Moving to
  the trash 37 of 203`. **Stop** finishes the current frame and keeps changes
  already made. Large removals over a network share no longer time out in the
  browser.

- Stopping or restarting the server no longer hangs until systemd kills it.
  Background work stops at its next safe point: a quality scan saves what it
  measured, a stack build checkpoints the frames it integrated and resumes
  after the restart, and imports and calibration grading stop at a commit.
  The log lists jobs that have not stopped yet. A stack build stopped this
  way no longer counts toward the two restarts that drop a build.

- Restarting the server from the desktop app's Settings waits for the old
  server to finish its work, so the job queue it saves is not lost. If that
  work is still running after two minutes, the log lists it and the whole
  app restarts instead.

- **Settings › Server** can fix the desktop app's localhost port, so browser,
  API, and agent connections keep the same address across restarts. A port
  conflict shows the error and Server settings so you can choose another
  port or return to Automatic.

- `--allow-database-management` now guards only what lets a client choose a
  server path: registering or changing databases and their folders, storage
  folders and limits, the PixInsight program and runs folder, a WBPP run
  folder outside that runs folder, imports from outside the image folders,
  local exports to a chosen path, and the new-frame and calibrated-copy
  switches. An editor no longer needs it to keep calibration frames out or
  use them anyway, mark their validity, forget them, clear masters,
  invalidate flat coverage, move targets and exposures, set exposure
  grouping or the AstroBin filter map, fill in GUIDs, run WBPP, install Seiza
  catalogs, manage and sync with peers, pair clients, or move rejects to the
  trash and back. Viewers get none of these. Only an editor reads a WBPP
  run's files, a link in a run folder can no longer lead outside it, and a
  calibration frame recorded outside the database's folders shows as
  missing instead of being read.

### Backups, settings and desktop

- **Settings › Backups** backs up PSF Guard's settings, accounts, setups and
  Planning's store, and every catalog with the tables PSF Guard adds to it,
  into one zip archive with a manifest of versions and checksums. Download
  the archive in a browser or save it to a folder in the desktop app, or
  turn on scheduled backups: daily or weekly at a time you choose, to a
  folder you choose, keeping the newest few or those younger than some
  days. Scheduled backups wait for work you start and show progress in the
  job list, where you can stop them. They remove only their own older
  archives. Peer keys and tokens
  are included by default in manual desktop backups and new desktop
  schedules, and excluded by default in a browser. `psf-guard backup` supports
  both scopes, `--dry-run`, and `--include-secrets`. CLI backups exclude
  secrets by default. Restore archives manually; see [Backups](https://github.com/theatrus/psf-guard/blob/v0.12.0/docs/BACKUPS.md).

- Backups suggest `~/Documents/psf-guard/backups` and create it when it is
  missing. In the desktop app they include secrets unless you untick
  **Include secrets**. Settings › Backups still shows how the last backup
  went after PSF Guard restarts.

- After a successful browser sign-in, PSF Guard reloads the current URL to
  load the server's current UI. PSF Guard checks that the session was saved
  before reloading. Failed sign-ins stay on the login form.

- **Server information** scrolls long database lists inside the dialog while
  the heading and close controls stay visible. Database IDs, files and image
  folders have separate labels, and long paths wrap on small screens.
  Server details and the database list have separate loading and error
  messages. **Retry** reloads only the failed request.

- The desktop app offers **Zoom in**, **Zoom out** and **Reset to 100%** in
  the hamburger menu. Cmd/Ctrl with +, − or 0 changes the whole UI from 50%

### Agents and collaboration

- An agent connected over MCP can now work with flats and backups. It reads
  each rig's flat groups, the changes between them and the dust they show,
  the masters and lights that use a group, a calibration frame's dust, and a project's
  calibration scope; it can split or join groups, put lights on a side of a
  change, override a suspect frame with **Use anyway**, check and repair calibration
  duplicates with the check's token, pause and resume the quality analysis,
  preview pre-generation, flat measuring and frame-site reading with
  `pause_job` and `resume_job`; and create a backup (settings only, unless
  the request includes every catalog). `get_jobs` lists every background job,
  `explain_calibration` can keep only the flats, and each write needs the
  same access and database management as in the app. Backups through MCP
  never include secrets and never hand an archive out. See
  [the MCP guide](https://github.com/theatrus/psf-guard/blob/v0.12.0/docs/MCP.md).

- Collaboration imports preserve Starfront's physical-filter/data-band mapping
  and OSC camera and Bortle limits in reviewed plans. Reports carry the data
  bands explicitly, and work for bands disabled by the project stays held.

- Collaboration **Reports > Contribution files > Upload pending** sends raw accepted lights
  with the same matched calibration inputs as exports, or an existing PSF Guard
  or WBPP stack. Matching and validation run in the background; only exceptions
  require review. Upload manually, or opt into automatic raw/PSF Guard
  stack delivery for the rig's database. **Transfers** in background activity
  shows progress, Pause, Resume, Retry and Cancel. Completed-file receipts
  survive restart; interrupted files retry without duplicating server files.
  Delivery receipts are shared across jobs by destination and file content revision,
  so shared calibration files are not repeatedly uploaded. Automatic raw delivery
  queues new exposures and changed source revisions. Retrying an exception checks
  the current remote owner's receipts, and automation settings wait for their
  saved policy before allowing edits.
