# v0.11.0

PSF Guard 0.11.0 plans targets across your rigs and writes each plan into
the rigs' Target Scheduler databases, gives stacks a view of their own, and
lets AI agents work with your catalogs. Target Scheduler, with the PSF Guard
Sync plugin, stays the main way to run a rig. Pairing a rig with the
N.I.N.A. Director plugin, and collaboration through AstroCollab, are early
betas.

## Highlights

- **Planning.** Frame a target on survey images or N.I.N.A.'s offline sky
  maps, set goals per filter, share the work between rigs, see when the
  target is up from each, and, after a preview, write the plan into each
  rig's Target Scheduler database. Plans sit in the Library beside the
  projects they shoot.
- **Stacks** has a view of its own beside Images and Sequence, a new default
  stacking method that weights frames by noise, one build per channel, colour
  composed once the last channel is in, and WBPP runs started from the same
  page.
- **Calibration** prefers a complete set of darks at the sensor's set point,
  keeps darks that caught stray light out of masters, finds the lights the
  library cannot calibrate, and pairs calibrated copies from WBPP, Siril and
  other tools with their raw lights.
- **Agents.** PSF Guard is an MCP server: Claude Code, Codex or another agent
  can read and change catalogs, plans and stacks as the user who connected
  it, within the same limits as the app. **Connect an agent** sets one up in
  one step.
- **Quality** scans measure each frame's signal-to-noise against Gaia stars,
  so haze and a bright sky lower a frame's score.
- **Storage.** Stacks and masters can live on their own volumes, a disk limit
  clears old previews first, old stacks and masters no longer pile up, and
  **Purge Rejects** moves long-rejected frames to a trash folder you can
  restore from.

## Upgrading from 0.10

- **The first start takes longer.** PSF Guard backs up each catalog once
  before its calibration tables gain three columns, and a background pass
  then measures every raw dark. On a NAS this can take minutes.
- **Every stack and master rebuilds once**, the first time it is used,
  because the stacking engine changed. Colour composites rebuild too.
- **The cache has a disk limit.** When its volume passes 90% full, PSF
  Guard deletes old image previews first, then old stack checkpoints, then
  masters unused for a week that it can build again; never stacks. **Most
  of the volume to use** in **Settings › Storage** sets the limit; 100
  turns it off.
- **Planning adds a table to each catalog.** Where database management is
  on, as it always is in the desktop app, the first Library listing writes
  a `psf_guard_catalog_identity` table into each registered database.
  Target Scheduler ignores it.
- **Docker keeps its settings on `/data`.** The registry, browser users and
  planning store now live in `/data/config/psf-guard`, and the cache in
  `/data/cache`. If you mounted `/home/psfguard/.config` to keep them, copy
  its `psf-guard` folder into `/data/config/` before you start 0.11, or the
  server starts without your databases and users.
- **Going back to 0.10.5 costs something.** Once 0.11 has opened a catalog,
  0.10.5 refuses to import, upload or sync into it until you run
  `UPDATE psf_guard_calibration_schema SET version = 8;` on that catalog;
  0.11 repeats its upgrade harmlessly later. 0.10.5 may delete stacks that
  0.11 built, and rejects 0.11 moved to the trash come back as Pending when
  0.10.5 imports that folder.

## Added

### Planning

- **Planning** turns each project into a plan. Every registered database is
  a rig, and projects that share a Target Scheduler GUID across databases
  form one plan shot by several rigs. Plans sit in the Library beside the
  projects they shoot; plans with nothing captured yet have a section of
  their own, with **New plan**. **Planning**, on a Library card or in the
  header, opens the plan's workspace at its own address
  (`/plan?plan=<key>`), so a link opens the same plan on any PSF Guard that
  holds those databases. The workspace has **Framing**, **Exposures**,
  **Rigs** and **Priority and defaults** tabs under a summary, and one save
  bar that names what changed and asks before you leave with edits unsaved.
  Planning is on for every server and keeps its store in
  `director-meta.sqlite` beside the database registry (`--director-meta`
  moves it); a server without database management drafts plans but does not
  write to rig databases. If the store will not open, PSF Guard starts with
  Planning off and the log says why.
- Projects already in Target Scheduler become plans with their targets,
  mosaic grid, priority and exposure plans filled in, and follow changes
  made in N.I.N.A. until you edit them in Planning. After an activation,
  **Take Target Scheduler's values** brings frame counts, templates,
  exposure lengths and moved targets from N.I.N.A. back into the plan. A
  project of several separate targets stays with Target Scheduler, with a
  warning.
- The **Framing** tab works like N.I.N.A.'s framing assistant. The rig's
  field is a rectangle on the sky: drag it to move the target, turn it by its
  handle, click a quarter turn or the rig's fixed camera angle, and lay out a
  mosaic with overlap. Drag the rectangle over a still sky, or pin it and
  move the sky; **Turn the sky with the camera** keeps the rectangle upright.
  The sky turns as a globe from three arcminutes out to a hemisphere, with a
  coordinate grid, constellations, and survey images (DSS2, SDSS, DESI
  Legacy, 2MASS, the H-alpha map and the narrowband layers) that the server
  caches for offline use.
- **Find a target** offers names from the server's own catalog as you type,
  with no network, and looks others up once at CDS Sesame; **Undo** and
  **Back to saved framing** take you back. Marks show deep-sky objects at
  their size and angle, comets and asteroids, and the Sun, Moon and planets;
  choose catalogs under **Catalogs marked** in **View**.
- `psf-guard sky-maps install full|nsns-ohs|nsns-ohs-starless` installs
  N.I.N.A.'s offline sky maps. Framing then draws from them with no network,
  in place of the matching online survey.
- Each rig has an **On** switch on the Framing tab, so several rigs can shoot
  one plan. A rig can share the plan's framing or take a separate one with
  its own grid, camera angle, panel size and center, drawn in its own colour;
  its swatch picks the rig whose field sets the shared panel size. In a
  mosaic, each rig can own some panels, and the plan names any panel no rig
  covers. Each activated panel's latest stack is drawn where its plate solve
  puts it: the best one, a colour composition, or one filter.
- A visibility chart under the sky shows tonight, noon to noon, for each rig:
  altitude against its horizon, the Moon, twilight, the meridian transit and
  the rig's meridian pause, within the plan's scheduling limits. It lists a
  week of nights and estimates how many nights each rig needs for its share.
- The **Exposures** tab sets goals per filter in accepted hours or frames,
  and per rig the exposure template and length that meet them. A rig can
  carry its own goal; for an hours goal, a rig far from f/5 is offered one
  that reaches the same depth, such as 24 h at f/10 for 6 h at f/5. Switching
  between hours and frames converts through the exposure length. Each rig
  shows accepted frames against desired, with taken and rejected counts.
- **Settings › Exposure templates** is a shared template library, so a rig
  whose database has no template for a filter can still join a plan;
  activation writes the template into that database.
- Activation writes the plan into each rig's Target Scheduler database after
  a preview: a project per rig, a target per mosaic panel and an exposure
  plan per goal. It takes over the targets and exposure plans a project
  already has instead of adding twins, and never touches captured frames or
  grades. Turning a rig off sets its project Inactive; work the plan drops is
  switched off, not deleted, and comes back with its frames. A panel moved
  after it has frames gets a new target. A busy or read-only rig database
  fails only that rig. Planning reads rig databases without locking them, so
  N.I.N.A. keeps working, and reads "On the rigs" once they hold the plan.
- Plan Target Scheduler's scheduling limits (altitude, custom horizon and
  offset, meridian window, dither, filter switch, minimum time, smart
  exposure order) as defaults for every plan, a site or a rig, or for one
  plan. Activation writes them into each rig's project, so they hold without
  PSF Guard. A rig can also apply its limits to every project in its
  database, including ones made in N.I.N.A., after a list of what will
  change.
- On the **Rigs** tab, **Add a rig** starts a new project in a rig's database
  or merges in a project another plan holds, so two rigs that each made a
  project for one target become one plan. **Detach** splits one off again,
  and asks first when that drops planned work.
- A rig at another site can be planned here. Set **Remote site** in the rig's
  setup to the Sync peer that holds its database; activation then pushes the
  same Target Scheduler rows there, and **Push again** resends them when the
  site was offline.
- **Settings › Rigs** holds each rig's setup: optics (**Use frame headers**
  fills them from the newest frame), site, and **Limits and delivery**.
  Sites hold a location and a horizon: paste or upload a N.I.N.A. `.hrz`
  file, for a site or for one rig that differs, and download it back.
- A database file copied by hand is named as a copy and left out of
  planning, so two files never pass for one rig.

### Director plugin (early beta)

- Pairing a rig with the N.I.N.A. Director plugin is an early beta; Target
  Scheduler with the PSF Guard Sync plugin stays the main way to run a rig.
  A plugin paired with a one-use code pulls its rig's program from the
  activated plans, valid for 24 hours so the rig keeps working through a
  network outage, then checks in saved frames and reports what it is doing.
  A rig's program changes only when you activate again. Programs follow the
  project order set under **Priority and defaults** and each template's
  per-filter Moon avoidance.
- **Live** on the Sky, opened from the header's Live chip, draws each
  reporting rig where it points and lists whether it is online, quiet or
  offline, its current operation and for how long, when it last pulled its
  program and checked in, and frames waiting for grading. The chip turns red
  when a rig goes quiet.

### Collaboration (early beta)

- Collaboration is an early beta. Rigs can take part in AstroCollab projects. A rig's **Collaboration** tab
  in **Settings › Rigs** registers it with a server through **Connect
  server**, by browser sign-in or pairing code; PSF Guard keeps the
  credential in its config folder with private file permissions. Browse and join
  projects, **Pull tonight's work** for the rig's site and Moon, review it,
  **Import draft** as an inactive project, and activate safe assignments
  into the rig's database. **Pull tonight automatically** pulls once per
  observing night. Accepted images are offered for review, with their
  guiding, HFR and Moon data, as they arrive, and contributions go out with
  fresh plate solves. Optional live activity sharing keeps target names and
  coordinates private.

### Stacks

- **Stacks** sits beside **Images** and **Sequence** in the header and holds
  the stack previews that used to sit above the image grid. It stacks every
  frame of the project or target in scope; **Stack selected** in Images
  opens it with a hand-picked set, and Library cards open a project's
  **Sequence** and **Stacks** directly. **Stack in WBPP** sits beside
  **Build stacks**, and a run's masters appear as stacks when it ends, with
  a colour preview from the channels you choose. Cards fill the row until
  you choose a **Card size**; **Fit** goes back.
- **Settings › Stacking** sets how stacks integrate their frames.
  **Recommended**, the default, normalizes the local background without
  seams at frame edges, weights frames by their noise, picks the reference
  from each frame's stars and sky, registers with a quadratic fit for lens
  distortion, and resamples with Lanczos-3. **Draft** skips the final
  rejection pass for a quick look, and **Classic** keeps the 0.10 method.
  Bayer drizzle is there for dithered colour frames, and automatic previews
  moved to the same tab. Stacks built before the upgrade show as out of date
  until rebuilt. `psf-guard stack-snr --weight-by-noise` weights frames from
  the command line.
- Review a mosaic's panels together. The header's target switcher offers
  "M31 mosaic (4 panels)" when a project's targets form one mosaic: Images
  groups frames under each panel, Sequence shows every panel's frames in
  capture order, and Stacks lays each panel's stack out as the grid and on
  the sky. Grading and stacking stay per panel.

### Calibration

- Find the lights the calibration library cannot calibrate: no matching
  flat, no bias or dark, or flats more than 60 days away (**Settings ›
  Calibration › Flat age limit**; 0 lifts it). Each rule counts only where
  the library holds that kind for the camera, so a rig that never shoots
  flats is not affected. In a project's **Calibration** report, **Check
  lights** lists them and **Reject N lights** rejects them, so Target
  Scheduler shoots them again. **Leave out lights that can't be calibrated**
  keeps them out of stacks; the stack card counts them under **can't
  calibrate**, and each frame says why.
- Darks that caught stray light, such as dawn through an open roof, stay out
  of masters and WBPP exports. PSF Guard measures each dark once in the
  background, marks one that sits well above its matching darks in the
  calibration library, and names the frames it left out.
- A stack's calibration masters show the sensor temperatures and nights of
  the frames behind them in the master inspector, so a master shot warmer
  than its lights stands out.
- Building calibration masters shows progress on the stack card and in the
  header queue: the master, what Seiza is doing with it, and the frame or
  tile under way. **Stop** ends a master build part way.
- Calibrated and registered copies from WBPP, Siril, ASTAP, DeepSkyStacker
  and other tools pair with the light each came from, on import, in sync and
  after each folder refresh, instead of importing as extra lights. A
  calibrated copy with no raw frame becomes the light until the raw arrives
  and takes over, grade and all. In the image detail, **V** or the buttons
  beside the image switch between a frame and its copies; grid cards mark
  frames that have them, and the reject archive moves copies with their
  light. Per database in **Settings › Databases**, **Pair calibrated and
  registered copies with their lights** turns pairing off, and **Measure
  quality on the calibrated copy** scores frames from their calibrated
  pixels, compared only with other calibrated frames.

### Agents and API tokens

- PSF Guard is an MCP server at `/api/mcp`. An agent such as Claude Code or
  Codex can read catalogs, images, grades, quality evidence, sequences,
  stacks (as images too), calibration and plans, and can grade, import,
  scan, stack, run WBPP, edit projects, targets and exposure plans,
  plate-solve, predict satellites, preview and apply syncs and activations,
  and remove or restore rejects. `explain_calibration` says why a light got
  or missed each master. Every tool runs through the same API as the app, as
  the user who connected the agent, so roles and database management limit
  it as they limit a person. A client pointed at the server's bare address
  is told to use `/api/mcp`. See `docs/MCP.md`.
- **API tokens** for scripts and agents: mint one under **Settings › Users ›
  API tokens** or with `psf-guard users token create`, and send it as
  `Authorization: Bearer psfg_…`. A token acts as its user, can be read only
  or expire, and shows once. Revoke it there or with `users token revoke`;
  removing a user revokes their tokens. **Connect an agent** mints a token
  and shows the setup to paste into Claude Code or Codex. A server without
  accounts has a **Settings › Agents** tab with the setup for this machine.

### Storage and rejects

- Stacks and calibration masters can live on their own volumes. Set them
  with `--stack-dir` and `--calibration-dir` (or `stack_directory` and
  `calibration_directory` under `[cache]`), or under **Settings › Storage ›
  Folders**, which also sets the cache folder. A folder changed in Settings
  takes effect at the next start, which moves the files first; if a move
  fails, PSF Guard moves them back and keeps the old folder.
- **Settings › Storage › Disk use** shows how full each volume is and what
  it holds. Past **Most of the volume to use** (90% by default), PSF Guard
  deletes image previews on that volume, least recently viewed first, then
  stack checkpoints a day old or more, then masters unused for a week that
  their frames can build again. It never deletes stacks, color previews or
  WBPP masters. Stacks and masters can have limits of their own.
- Old stacks and masters no longer pile up. Each hour, in every database,
  PSF Guard removes stacks a newer build replaced, stretch and deconvolution
  results unused for a week, the stacks of deleted projects, half-written
  masters, and masters a newer one replaced once they have gone a day unused
  with no stack naming them. Over the disk limit, masters unused for a week
  go too. A stack checkpoint goes once a build must restack from scratch, or
  after 30 days unused. PSF Guard keeps a master whose frames are gone or
  that the catalog does not record, and builds a removed master again when a
  stack needs it.
- **Purge Rejects**, beside a database's **Import** in **Settings ›
  Databases**, previews the frames rejected at least N days ago (7 by
  default) and takes them out of the catalog. Their files and copies wait in
  a `.psf-guard-trash` folder, and **Restore** brings a batch back until the
  trash empties, 14 days later by default; **Purge** then forgets the
  batch's records. The CLI has the same steps: `remove-rejects`,
  `restore-removed`, `list-removed`, `empty-reject-trash` and
  `purge-removed`. Sync, imports and uploads leave removed frames out, and
  plan progress still counts them as rejected.

### Elsewhere

- Quality scans measure each frame's photometric zero point against Gaia
  stars and its sky noise, so signal-to-noise joins star count and HFR in
  the quality score. A frame dimmed by haze or shot under a brighter sky
  scores lower than frames of the same exposure, from any night. Frames
  scanned before need **Rescan All Quality** to gain it.
- An open browser tab notices a server update: a **PSF Guard was updated**
  bar offers **Reload now**, and the tab reloads itself the next time you
  change views; unsaved plan edits still ask first.
- **Fill in GUIDs**, in **Settings › Databases**, repairs a Target Scheduler
  database whose upgrade past schema 22 in one step left rows without GUIDs,
  which hid those projects from Planning. It backs the database up beside
  itself and fills only the empty ones; `psf-guard fill-guids` does the
  same.
- Seiza 0.24 opens more FITS files: images in an extension or tile-compressed
  (fpack), signed 16-bit images, whose negative values used to read as zero,
  and 64-bit integer images. Blank pixels read as missing, and `HIERARCH`
  keywords are kept.
- In the desktop app, every folder and file setting has a **Browse…**
  button: storage folders, PixInsight and its runs folder, a WBPP run's
  folder, the export path, and the database form's directories.
- The Linux AppImage and .deb carry AppStream metadata, so software centres
  show a summary, a description and screenshots.

## Changed

- The Overview is now the **Library**. It opens compact: one row of pills
  per project with its database, state, progress, grading counts and dates,
  and a plan shot by several rigs wrapped in an outer pill that sums them. A
  row opens into the full card and folds back with its arrow; **Compact**
  and **Detailed** switch the whole list, and **Settings › Review** sets
  which one it opens in. A **Show** select (Active, Still to shoot, Done,
  Draft, Inactive, Closed, and No database with Planning on) and the search
  box narrow it and stay in the URL. Where the server allows database
  changes, a row's state pill changes the project's Target Scheduler state.
- The header reads from the whole to the part: **Library**, the project (a
  plan shot by several rigs is one row with its rig count, found by typing
  any rig, database or target), **Planning**, the rig and target, then
  **Images**, **Sequence** and **Stacks**, then **Sky**. Images, Sequence and
  Stacks wait until you choose a project or database. The header keeps to
  one row when it fits, and **Stats** moved to the image grid.
- The Overview's **Plan & coordinates** dialog is gone. A Library card's
  **Planning** button opens the project's plan, whose **Rigs** tab holds each
  rig's Target Scheduler settings.
- Settings has new tabs: **Calibration** (moved from Setups), **Stacking**,
  **Storage**, **Performance**, and, with Planning, **Rigs** and **Exposure
  templates**.
- Dark and bias masters prefer a complete set at the sensor's set point over
  a nearer handful at another temperature. Before, two warm darks shot near
  the lights could beat dozens at the set point and leave row banding in the
  stack. **Settings › Calibration › Dark choice** sets it; **Nearest set**
  keeps the 0.10.5 rule. WBPP exports follow the same choice, and stacks
  whose masters change rebuild.
- The header's background work is one small chip with overall progress and a
  job count. Open it to see every catalog refresh, quality scan, stack build
  and WBPP run on any database; reorder waiting stack builds and WBPP runs,
  take one out of the line, or stop the running job after one question.
  Click a job to open what it works on. A quality scan that ended with errors
  stays on the chip, linked to its target, until you dismiss it.
- The job queue survives a restart: stack and colour builds come back in
  order and waiting WBPP runs keep their place; a run the restart cut off
  shows as stopped. With automatic previews on, every database is checked
  once after a start, so frames that arrived while the server was down reach
  their stacks.
- **Settings › Performance › Processor use** sets the share of cores for work
  you wait on and for background work, without a restart. Background stack
  refreshes, quality scans in every database and preview pre-generation
  share one background budget, and each job keeps Seiza inside it. Previews
  you look at, plate solves, star lists and PSF views still use every core.
- Image cards take about a third of the room for their text: filter, time,
  HFR and stars on one row, and the grade a slim strip with the reject reason
  beside it. A narrow card keeps the time for this year's frames and the year
  for older ones. The target's name is left off when every card shows the
  same target.
- The image grid's **Filter**, **Flag** and **Status** take several values,
  so Ha and OIII together, or everything but Rejected, is a few clicks;
  links with one value still work. The toolbar holds still: a long choice no
  longer pushes controls onto a new line, and every control shares one
  height.
- Stacks keep different exposure lengths apart by default, so 120 s and
  300 s frames build separate stacks instead of dimming each other. A project
  can turn **Separate exposure groups** off, and one that already chose keeps
  its choice.
- **Build stacks** queues one build per channel, and a channel already built
  as asked returns at once. Once a target's last channel is in, its colour
  previews are composed again from the new stacks, and a target with none
  gets its first: LRGB, else RGB, else narrowband.
- Automatic refresh restacks only the channels whose frames or grades
  changed. **Also stack channels that have no stack yet** stacks channels as
  their frames arrive, by default those with a frame from the last week; set
  the window in days, or clear it for channels of any age.
- Stacks build sooner. Frames are prepared several at once on the build's
  own workers, and Seiza 0.23 builds masters on every core and speeds up
  stacking, debayering, stretches, background models and deconvolution, with
  the same output. Existing stacks and masters rebuild once, as after every
  Seiza stacking upgrade.
- Stack progress keeps moving through the final rejection pass instead of
  sitting at 100%.
- Quality scans and backfill plate-solve several frames at once, up to the
  background share.
- The image detail's sky overlay stays as you last left it, instead of
  turning on for every solved frame, including frames quality analysis
  solved on its own.

## Fixed

- A frame where N.I.N.A. Fast finds no stars but HocusFocus finds some is
  measured instead of reported as a failed scan. It scores on HocusFocus's
  count, and its details say which detector counted.
- A master dark that records no sensor temperature, such as one from
  PixInsight's WBPP, now calibrates cooled lights; before, the stack ran
  uncalibrated.
- Colour previews with background extraction no longer tint the corners. All
  channels now share one background model; one per channel had left some
  previews green in one corner and magenta in the opposite one.
- Twilight flats in folder imports and remote uploads go to the calibration
  library and no longer create light rows or exposure templates that could
  sync back to Target Scheduler. A few short frames in a folder import no
  longer set a new template's default exposure.
- A queued WBPP run keeps its place at the head of the line when its
  database is busy as its turn comes, and two starts at once can no longer
  launch two PixInsights.
- With previews set to JPEG, background pre-generation writes the file the
  viewer asks for. It saved JPEG data under a `.png` name, so the viewer
  rendered every image again.
- A large image grid scrolls smoothly. Every card ran a hidden spinner that
  never stopped, so the browser restyled thousands of cards each frame;
  Safari felt it most. Cards off screen now skip drawing until they come
  near.
- The Sequence view's Scoring panel has its own background and border, and
  its limit boxes fit inside it. A few other borders and text colours that
  named missing theme colours show again.
- A colour stack's processing panel no longer fails without a word. An
  RC-Astro value outside the tool's range, such as BlurXTerminator's Sharpen
  Stars above 0.7, is marked on its field and stops Apply with the reason,
  and a refusal from the server shows beside the button you pressed. Mono
  stacks check the same ranges.
- With a target chosen in the header, Stacks shows only that target's stacks
  and colour compositions, not every panel of a mosaic.
- Blind solves use the blind index beside the star catalog. A catalog in a
  folder of its own (the `stars` setting or `SEIZA_STAR_DATA`) took its index
  from `data_dir` or Seiza's default folders, which could belong to another
  catalog, and with none there blind solving was off. `blind_index` or
  `SEIZA_BLIND_INDEX` still chooses one.
- Satellite tracks are predicted with the WGS72 constants their orbital
  elements were fitted with, which moves a track by up to tens of
  arcseconds; the next quality scan recomputes each prediction. FITS header
  values written without a space after `=` read correctly.
- The Docker image keeps everything it writes on the `/data` volume: the
  database registry and users, the cache of previews, plate solves, quality
  scans and stacks, and Seiza catalogs installed in Settings, so an image
  update no longer loses them (issue #450). The image includes `curl`, and
  the example `docker-compose.yml` has a healthcheck that works before the
  first login.
- The server no longer lets the browser keep the page for an hour, so a
  reload always brings the new version.
- A server started with `--static-dir` serves only files inside that folder;
  a path with `..` in it could read any file the server could. The default
  server, which carries the app inside its binary, was never affected.
